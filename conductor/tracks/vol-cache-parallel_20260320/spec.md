# Specification: Volume Cache Parallel Read-Path

**Track ID:** vol-cache-parallel_20260320
**Type:** Feature
**Created:** 2026-03-20
**Status:** Draft

## Summary

Upgrade the Volume LRU slice cache to support high-throughput concurrent readers and add a background prefetch queue, eliminating the cache as a serialization bottleneck when texturing algorithms run on multiple threads.

## Context

When `texturing-parallel_20260320` adds OpenMP parallelism to texturing loops, each worker thread will scatter-read voxels across many volume slices simultaneously. The current LRU cache uses a single `std::shared_mutex` for all operations: reads take a shared lock (fine), but LRU eviction on every cache miss takes an exclusive write lock — serializing all threads on every cold miss. Additionally, there is no prefetching: every cache miss blocks the requesting thread on synchronous TIFF disk I/O. These two issues together mean naive OpenMP parallelism on the pixel loops may not scale.

This track fixes the read-path before parallelism is added. Depends on `vol-abstract-iface_20260320` (Volume base class must exist before we add prefetch as a virtual optional API).

## User Story

As a developer parallelizing texturing algorithms, I want Volume slice access to scale with the number of reader threads so that adding more cores produces proportional throughput gains rather than lock-contention regression.

## Acceptance Criteria

- [ ] Concurrent reads to cached slices complete without serialization (no exclusive lock taken on cache hit)
- [ ] Concurrent cache misses for different slices load in parallel (per-slice locks, not a global write lock for the load)
- [ ] A prefetch API exists: `volume->prefetch(std::span<int> sliceIndices)` submits background loads
- [ ] Background prefetch does not starve foreground reads
- [ ] Thread-safety is verified by a stress test: N threads reading random slices concurrently with no data races (run under TSan)
- [ ] Existing single-threaded behavior and test suite unchanged

## Dependencies

- `vol-abstract-iface_20260320` — Volume base class must exist (prefetch API goes on the base or as a mixin)

## Out of Scope

- Changing the on-disk TIFF format or adding new storage backends (see `vol-zarr-backend_20260320`)
- Per-thread local caches (considered, deferred — global prefetch cache is sufficient for initial parallelism)
- Prefetch heuristics tuned to specific access patterns (add as follow-on once benchmarked)

## Technical Notes

**Current lock structure in `Volume.cpp`:**
- `std::shared_mutex cacheMutex_` — guards the `LRUCache` data structure
- `std::vector<std::mutex> sliceMutexes_` — one per slice, prevents duplicate concurrent loads
- On cache miss: acquires `cacheMutex_` write-lock while inserting loaded slice → all readers serialized

**Proposed fix — two-phase load:**
1. Check cache with shared lock (fast path, no exclusive lock needed)
2. On miss: acquire per-slice lock, re-check (double-checked locking already in place), load synchronously
3. After load: acquire write lock only to insert into LRU (brief critical section, no disk I/O under the write lock)

**Prefetch API sketch:**
```cpp
// On Volume base class (no-op default impl):
virtual void prefetch(std::span<const int> sliceIndices) {}

// On TIFFVolume:
void prefetch(std::span<const int> sliceIndices) override;
// Submits indices to a thread pool queue; workers call cache_slice_()
// Background loads use the same per-slice mutex to avoid duplicate work
```

A simple `std::thread` + `std::queue` or a small `BS::thread_pool` (or OpenMP tasks) is sufficient. Limit to 2–4 background loader threads to avoid saturating disk bandwidth.

**libcore ObjectCache as a replacement candidate:**

`educelab/libcore` (`~/source/libcore/include/educelab/core/utils/Caching.hpp`, also at github.com/educelab/libcore) provides a templated `ObjectCache<T>` with:
- Pluggable eviction policy (default: `LRUPolicy`) and sync policy
- `SynchronizedObjectCache` alias using `ExclusiveRWSyncPolicy` (`std::shared_mutex` + `std::lock_guard` for writes, `std::shared_lock` for trivial reads)
- Size-limited eviction with per-object byte accounting
- `find()` for atomic check-and-retrieve (important for concurrent callers)

Consider adopting `ObjectCache` to replace the hand-rolled LRU in this project. Key caveat: `ExclusiveRWSyncPolicy` still takes an exclusive write lock during `insert()`, which is the same bottleneck identified above. The two-phase load strategy (load slice outside the lock, then insert briefly under write lock) would need to be implemented in the `Volume` layer on top of `ObjectCache` — the cache itself just needs to guarantee that `insert()` is the only exclusive section. Alternatively, a custom `SyncPolicy` could be contributed upstream to libcore that implements this pattern more explicitly.
