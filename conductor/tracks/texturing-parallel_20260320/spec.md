# Specification: Parallel PPM Generation & Texturing

**Track ID:** texturing-parallel_20260320
**Type:** Feature
**Created:** 2026-03-20
**Status:** Draft

## Summary

Parallelize the pixel-iteration loops in `PPMGenerator` and all four texturing algorithms (`IntersectionTexture`, `CompositeTexture`, `LayerTexture`, `IntegralTexture`) using OpenMP, yielding near-linear speedup on multi-core machines for the embarrassingly parallel per-pixel work.

## Context

PPM generation and texture generation are the two slowest pipeline stages for large scrolls. Both iterate over millions of pixels with no data dependency between iterations — the definition of embarrassingly parallel. OpenMP is already linked into `vc_texturing` but unused. The per-pixel work (ray-triangle intersection for PPM; trilinear interpolation + neighborhood sampling for texturing) is CPU-bound after the Volume slice cache is warm. The Volume cache read-path fix in `vol-cache-parallel_20260320` is a prerequisite: without it, parallel threads serialize on the LRU cache write lock during cold misses, negating the speedup.

## User Story

As a researcher running `vc_render` or `vc_generate_ppm` on a 16-core workstation, I want texture generation to use all available cores so that a job that takes 2 hours single-threaded completes in ~10–15 minutes.

- [ ] `PPMGenerator::compute()` parallelizes the pixel loop with OpenMP; output is identical to single-threaded baseline
- [ ] `IntersectionTexture::compute()` parallelizes its pixel loop; output is identical to baseline
- [ ] `CompositeTexture::compute()` parallelizes its pixel loop; output is identical to baseline
- [ ] `LayerTexture::compute()` parallelizes its pixel loop; output is identical to baseline
- [ ] `IntegralTexture::compute()` parallelizes its pixel loop; output is identical to baseline
- [ ] Thread count is configurable via `setThreadCount(int)` on each algorithm (default: `omp_get_max_threads()`)

## Dependencies

- `vol-abstract-iface_20260320` — Volume base class (algorithms must accept `Volume::Pointer`, not `TIFFVolume*`)
- `vol-cache-parallel_20260320` — Cache parallel read-path required to avoid serialization on cache misses

## Out of Scope

- GPU (CUDA/Metal/OpenCL) parallelism — CPU OpenMP only for this track
- Parallelizing `AngleBasedFlattening` / `HierarchicalLSCM` (already handled via Eigen threading)
- Parallelizing mesh processing (`vc_meshing`) — separate concern
- Distributed (multi-node) processing

## Technical Notes

**PPMGenerator pixel loop** (`texturing/src/PPMGenerator.cpp:115–186`):
- Each pixel independently casts a ray against the BVH and writes to `ppm_->getMapping(y, x)`
- BVH tree and mesh are read-only — safe to share across threads
- PPM write at `(y, x)` — each pixel writes to a unique location, no false sharing if rows are independent
- `#pragma omp parallel for collapse(2) schedule(dynamic, 64)` over (y, x) is safe

**Texturing algorithm pixel loops:**
- All iterate `for (auto& [y, x] : ppm_->getMappings())` or equivalent
- `NeighborhoodGenerator` instances are NOT thread-safe (they have internal state) — each thread needs its own instance
- Use `#pragma omp parallel for` with a `firstprivate` or `threadprivate` `NeighborhoodGenerator`
- `volume->interpolateAt()` is safe to call concurrently after `vol-cache-parallel_20260320` lands

**Progress reporting:**
- Current: `progressUpdated(idx)` called per-pixel — high overhead, should be throttled
- Fix: emit progress only every N pixels (e.g., every 1000) or only from thread 0 in the OpenMP region
- `progressStarted` / `progressComplete` called outside the parallel region (no change needed)

**Output image writes:**
- All texturing algorithms write to `cv::Mat result_` at pixel-unique locations — no synchronization needed for the image write itself
- `LayerTexture` writes to `std::vector<cv::Mat>` — same argument, each pixel writes unique indices
